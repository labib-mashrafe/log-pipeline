Failed password lines are the best way to count failed logins. Why? -- Every time someone enters a wrong password, the log shows a line starting with "Failed password". Other lines from the same attempt, like "authentication failure" and "Invalid user", also appear, so counting them too would count one attempt several times. "Failed password" appears once per wrong password.

What I learned in Day 3

1. lines[:50] takes the first 50 lines. A number in square brackets after a colon is a slice.
2. if "Failed password" in line: keeps only the lines that contain those words.
3. A counter is count = 0, then count = count + 1 inside the if. The computer counts more reliably than I do by eye. I counted 10 and the real answer was 11.
4. .split() cuts a line into a list of words. Positions in a list start at 0, not 1.
5. Bug I found: pieces[12] gave the IP on line 6 but the port on line 29. The IP’s position moves because some lines have the extra words invalid user. A fixed position gives a silent wrong answer, not an error.
6. Fix: pieces[pieces.index("from") + 1] finds the word from first, then takes the word after it. That works on both line shapes.
7. A loop with an if and the fix inside it pulls the IP out of every Failed password line.
8. Data trap: line 30 says message repeated 5 times. It’s one line standing for 5 failures. I decide how to count it when I build the parser.

What I learned in Day 6

1. A count that adds up is a check. 633 + 1367 = 2000, and it matched the number I worked out separately. If the sum had been off, something would be wrong.
2. “Rejected” doesn’t mean broken. The log has many line types, and the parser only wants two. I looked at what was rejected instead of assuming.

4. The lowercase invalid user lines are copies of the same event, so rejecting them avoids double-counting.

What I learned in Day 8

1. HAVING vs WHERE: WHERE filters rows before they are grouped, HAVING filters the groups after the counting.
2. My threshold was 20 failed logins, and it flagged 4 IPs.
3. MIN(ts) and MAX(ts) gave me earliest and latest timestamp for each IP.
4. 112.95.230.3 made 26 attempts in 59 seconds, which means about one attempt every 2 seconds on average.
5. 103.99.0.122 made 46 attempts over about 2 hours, so it might be a human or a slow bot.
6. Count alone has two blind spots: A fast burst under the threshold slips through, but a slow spread over the threshold gets flagged by mistake.

What I learned in Day 9

1. The check I added: it looks through the rejected lines for “Failed password” and “Invalid user”. If it finds any, it counts them. Only when the count is above 0 does it print the error and stop.
2. Normal run result: parsed 633, rejected 1367, important lines rejected 0.
3. I broke the regex on purpose (an extra space after "from"). The check said 633 important lines were rejected, and it also said parsed 0 and rejected 2000. And then it printed the ERROR and stopped.
4. Why test a check by breaking things: A check that has never failed might be broken somehow, so I broke the regex on purpose with an extra space and saw it catch all 633 lines.
5. Why 1367 rejected is OK but 633 important rejected would not be: The rejected lines are fine because the parser wasn’t meant to handle them, but if important lines were rejected, that would’ve silently miss real attacks.

What I learned in Day 10

1. MONTHS is a dictionary that turns "Dec" into 12.
2. I use zfill(2) because it adds a 0. So “5” becomes “05”. Computers sort text one character at a time, left to right, and stop at the first difference. If we compare 2025-12-5 and 2025-12-10, the first 8 characters are identical. But computer puts 2025-12-10 before 2025-12-5 as “1” comes before “5”, which is wrong because Dec 10 is later. So if zfill(2) isn’t used, it causes wrong results.
3. I had to run db.py again because the table still had old timestamps (Dec 10 06:55:46), and db.py deletes them and replaces with the new format.
4. With "Dec 10", text sorting puts months in alphabetical order, so Dec looks earlier than Nov. With YYYY-MM-DD, the year comes first and the month is a number, so sorting as text gives the correct order.
